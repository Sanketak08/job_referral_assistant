---
name: job-search-phase
description: Discovers jobs strictly posted in the last 24 hours across tiered sources defined in profile.yaml (ATS APIs, target companies, EU open APIs, Indeed connector, JobSpy MCP for LinkedIn, extra boards like Xing), rejects roles requiring 5+ years, and outputs a timestamped CSV.
---
# Job Search Phase

All sources, companies, filters, weights and paths come from `input/profile.yaml` (`job_search`, `skills`, `locations`, `work_authorization`, `matching`). Never hardcode them here. If a value is missing in the profile, use the default noted in the step; do not invent data.

## Steps
0. **Check MCP servers**: Tavily, Playwright and Apify back the direct-form resolution, finalist verification and Tier 2 custom pages (`extra_boards` uses the venv's own headless Playwright, not the MCP). If any of them is not connected (on macOS this usually means Node/`npx` is not on the PATH Claude Code was started with), tell the user in one line which ones are missing and ask whether to continue without them. Do not degrade silently.
1. **Load Profile & Initialize**:
   - Read `profile.yaml`. Extract `job_search.target_titles`, `exclude_titles`, `seniority`, `experience`, `freshness`, `discovery`, `skills`, `locations`, `work_authorization`, `matching`, `output`.
   - Read every file in `job_search.output.dedupe_against` (default `output/applied_jobs.csv`, no header, column 1 = job URL) and build a set of normalized applied URLs (lowercase host, drop tracking params, but keep job-id params `gh_jid`, `jobId`, `job_id`, `jid`, `jk`, `id`: many career sites such as Stripe, Databricks and Trade Republic share one path for every job and differ only by `gh_jid`/`jobId`, so dropping the whole query would match every job at that company). Same rule as `norm()` in `fetch_ats.py`.
   - Get the current time once (`date`), in `system.timezone`. It is the reference for every age calculation and for the output filename.
2. **Prioritized Discovery** (run tiers in the order of `job_search.discovery.order`):
   - **Every tier is mandatory on every run:** Tier 1 `ats_apis`, Tier 2 `target_companies`, Tier 3 `eu_open_api`, Tier 3b `indeed_connector` and Tier 4 `jobspy_mcp` (LinkedIn + `extra_boards`). Never skip or cut a tier short because earlier tiers already found enough jobs, to save time or tokens, or because the user said "quick" or "just get the jobs". Only a tier the user has set to `enabled: false` in the profile is left out. If a tier errors, retry it once; if it still fails, finish the other tiers and report it (see step 6).
   - Before scoring, write one working-notes line per tier: `Tier <n> <name>: ran | raw <count> | fresh <count>` (or `FAILED: <reason>`). Do not move to step 3 until every tier has a line.
   - **Direct-form priority:** The goal is jobs the user can apply to on the company's own form without logging in anywhere. Tiers 1-3 (company ATS APIs) are the main source. Aggregator results (Tier 3b Indeed, Tier 4 LinkedIn and extra boards) are kept only if a direct application form can be resolved for them (`job_search.application_filters.require_direct_application_form`), by matching company + title against a direct-form ATS (`application_filters.direct_form_sources`: Greenhouse, Lever, Ashby, Workable, SmartRecruiters, Recruitee, Personio). Aggregator-only jobs and jobs that need an account portal (`drop_if_requires_account_portal`: Workday, Taleo, Oracle, SuccessFactors, iCIMS) are dropped.
   - **Tier 1 - `ats_apis`:** For every token in `ats_apis.boards` and `ats_apis.boards_verified` (all providers, including Workable, Recruitee and Personio) plus every ATS-backed `target_companies` entry, run `.venv/bin/python .claude/skills/job-search-phase/scripts/fetch_ats.py <fresh.json>`. It fetches each board's full listing in parallel (`max_parallel_requests`, timeout `request_timeout_seconds`), diffs it against the company snapshot (see **Company snapshot** below), applies the freshness rule, and writes the fresh jobs with a `why` field (`date` or `new_id`). A 404/timeout for one board is logged and skipped, never fatal. Tier 2 ATS companies are covered by the same run, so do not fetch them again.
   - **Tier 2 - `target_companies`:** Every target company is snapshot-tracked in `output/company_job_snapshot.json`, so career pages without posting dates still show which openings are new. API-backed companies (greenhouse, lever, ashby, smartrecruiters, workable, workday, and `ats: json` such as TomTom) are already covered by the Tier 1 `fetch_ats.py` run. For `ats: custom` companies, run `.venv/bin/python .claude/skills/job-search-phase/scripts/fetch_boards.py <companies.json> --group companies`: it loads each `careers_url` headless (following `page=N` up to `max_pages`), takes every link matching `job_link_regex` as a job, and diffs against the `custom:<name>` snapshot entries. Only URLs not seen before (`why: new_id`) count as new for these companies; never treat the whole listing as fresh, and never open them with `browser_snapshot` or Apify. A company that returns 0 links is a failure (its `job_link_regex` needs re-checking), not "no new jobs". For new custom-company jobs with an empty location, open the job page and read the location before the location filter. The first run for a company is a baseline (recorded, nothing flagged new).
   - **Tier 3 - `eu_open_api`:** Arbeitnow, JustJoinIT and Adzuna are fetched in code by the same `fetch_ats.py` run as Tier 1 (Adzuna reads `ADZUNA_APP_ID` / `ADZUNA_APP_KEY` from env or `.claude/settings.local.json`; an `adzuna:` line in the log means it failed). Do not call them again by hand. For any other enabled source, call `url` (fill `{page}`, `{query}`, `{country_code}` from `discovery.search_queries` and `countries`; add `headers`; read env vars named in the URL, skip the source if one is unset). Map fields with the source's `*_field` keys.
   - **Tier 3b - `indeed_connector`:** For each query in `search_queries` x each city in `locations`, call `search_tool` with `job_type` and the city's country code, stopping at `max_search_calls`. Results carry only a date ("Posted on"), so apply `freshness.date_only_sources_action`. Then apply the title, location and applied-jobs filters. For the survivors, call `details_tool` (up to `max_detail_fetches`) and run the experience, language and sponsorship rules on the full description. Dedupe by `dedupe_key`, keep the `to.indeed.com` URL as Job Link, and set `Source` to `Indeed`. A failed call is logged and skipped.
   - **Tier 4 - `jobspy_mcp`:** JobSpy covers LinkedIn only; Indeed comes from Tier 3b, and Xing, Reed, NoFluffJobs and BerlinStartupJobs come from `extra_boards`. Call MCP tool `search_and_filter` **once**. It runs every LinkedIn query group across `search_locations`, handles 429s with back-off, enforces `max_calls_per_run` and `max_runtime_minutes`, and applies the freshness, title, location, remote, applied-jobs, duplicate, experience, language and sponsorship rules of step 3 in code. It returns `summary` (counts, drop reasons, notes, `results_file`) and `jobs` (survivors with `skill_hits`, `must_have_missing`, `required_years`, `sponsorship`, `description_excerpt`). Treat those jobs as already hard-filtered: go straight to scoring (step 4), reading the full description from `results_file` when the excerpt is not enough. Jobs listed under `unchecked` in `results_file` (description could not be fetched) are not scored unless the user asks. If the jobspy server is not connected, run `.venv/bin/python .agents/jobspy_search.py` instead (same logic, prints the summary, writes the same file). Do not replace this with `scrape_free_job_boards` loops or an ad-hoc scraping script, and never skip its filters, even when asked to "just get the jobs": the filters are what make the results usable. Report the summary line (searches, raw, kept, minutes, notes) in the working notes. Then run `.venv/bin/python .claude/skills/job-search-phase/scripts/fetch_boards.py <boards.json>` for `extra_boards` (Xing, Reed, NoFluffJobs, BerlinStartupJobs). It loads each board headless, reads only job rows via the selectors in the profile, applies freshness (card age, RSS date, or new URL vs `output/board_job_snapshot.json`), and writes the fresh jobs in the same shape as `fetch_ats.py`. Do not open these boards with `browser_snapshot` or Apify. Its stderr line reports rows per board; a board with 0 rows means its selectors need re-checking, so say so in the working notes. Feed its jobs into step 3 like any other tier. If the jobspy tool errors or the server is down, follow `on_error` (Apify actor in `apify_fallback`, with `maxTotalChargeUsd` cap). Label `Source` with the real board name.
   - Every tier failure is logged in one line and the run continues (`on_tier_error`). Collect for each job: title, company, location, posted timestamp, link, description (if available), source, and any visa-sponsorship flag.
3. **Hard Filter (24 Hours + Experience)**: Apply in this order, discarding immediately; discarded jobs are never scored or output.
   - **Freshness:** Parse the publication time of every job (epoch ms/s, ISO 8601, or relative text such as "Posted Today"). Discard anything older than `job_search.freshness.max_age_hours` from now, EXCEPT jobs the snapshot flagged `why: new_id` (URL not in the company's previous snapshot, or first seen inside the window). Those count as fresh whatever their date says, and still go through every other filter. If a source exposes only a date, apply `job_search.freshness.date_only_sources_action`. If no date can be found, discard the job.
   - **Experience (new rule):** Search title + description with `job_search.experience.detection_patterns`. Take the lower bound of any range ("5-7 years" -> 5). Discard if the required years are `>= experience.reject_if_required_years_gte` (5). Also discard titles containing any `job_search.experience.reject_title_keywords` (Staff, Principal, Lead, ...). If descriptions were not returned by the source, fetch the job page/detail URL before deciding. If no year count exists anywhere, apply `job_search.experience.unknown_experience_action` (default keep).
   - **Language (new rule):** The candidate speaks English only (`job_search.language`). Discard postings written in German, Dutch, French, Spanish, Polish or Italian (detect from the description text, and from German title markers like "(m/w/d)"), and discard any posting that requires one of those languages, matching `job_search.language.required_language_patterns` (skip a match when `optional_markers` such as "plus", "nice to have", "bonus" sit within 60 characters).
   - **Sponsorship (new rule):** If `job_search.application_filters.drop_explicit_no_sponsorship` is true, discard postings whose text matches `outreach.sponsorship_check.no_patterns` (no visa/relocation/sponsorship, "must be based in", "must be eligible to work in"). The candidate needs sponsorship, so these applications cannot succeed. Postings that say nothing about visa/relocation are kept.
   - **Title/location/dedupe:** Discard titles matching `job_search.discovery.title_exclude_regex` or `exclude_titles`; keep titles matching `job_search.discovery.title_include_regex`, `target_titles`; keep only locations matching an enabled `locations.countries` entry by its `aliases` or `regions` (plus remote rules from `locations.work_mode`); discard URLs already in the applied set; collapse duplicates within the run by `job_search.output.dedupe_within_run`.
4. **Scoring**: Score each remaining job 0-100 against the profile using `matching.weights` (technical_skills, experience, role_title, location, sponsorship, other) and `matching.skill_group_weights`. Skills are matched via `skills.aliases`; `skills.must_have` missing -> heavy penalty; `matching.strong_match_signals` add; `negative_match_signals` subtract; sponsorship follows `work_authorization.sponsorship_matching` (explicit = high priority, unclear = never reject, ruled out = strong penalty). Drop jobs below `matching.minimum_score`. Rank descending. **Verify finalists before writing:** (a) fetch each finalist's full job page and re-apply the experience, language and sponsorship rules (search descriptions can be truncated or missing); (b) for LinkedIn/Indeed results whose company has an ATS token in `target_companies`, match the title against the company's own ATS posting and discard if its first-published time exceeds `freshness.max_age_hours` (aggregators re-post old jobs as new). Then keep the top `job_search.discovery.max_results_in_csv`.
5. **Dynamic Output Generation**:
   - Generate the current date and time using `job_search.output.date_format` and `output.time_format` (`YYYY-MM-DD_HHMMSS`).
   - Write the top results to `job_search.output.csv_path_template` (`output/daily_jobs_[DATE]_[TIME].csv`) with a script using the `csv` module (proper quoting, UTF-8).
   - The CSV must strictly contain these columns: `Job Title, Company, Location, Date Posted, Match Score, Ranking, Source, Job Link`. Location is the posting location as listed (city, country); Date Posted is `YYYY-MM-DD`. Job Link is the direct posting URL without tracking params.
   - Re-read the file to confirm it exists and has the header plus at least one row. If zero jobs passed, still write the file with only the header.
6. **Token Constraint**: Output only the file path upon completion. Do not generate conversational text or rationales. Exception: if any tier failed after its retry, print one line per failed tier (`Tier <n> <name> FAILED: <reason>`) above the path, so a partial search is never mistaken for a full one.

## Company snapshot (new-posting detection)
- File: `output/company_job_snapshot.json`, mapping `<provider>:<token>` to the job URLs seen at the last scan, each with a `first_seen` time. `fetch_ats.py` reads and rewrites it on every run. Do not edit it by hand.
- A URL missing from a company's snapshot is new, even if the posting has no date or a stale one. A job first seen within `max_age_hours` stays new on re-runs inside that window.
- Baseline: a company with no snapshot yet is only recorded, with nothing flagged new on that run. Detection starts from its second scan.
- Safeguards: a failed or empty fetch never overwrites a company's snapshot. If more than max(30, 50%) of a board's jobs look new at once, they are ignored and reported as an anomaly (the site likely changed its URLs).
- Not covered yet: Tier 2 `ats: custom` sites (Playwright), Tier 3 feeds, Tier 3b Indeed and Tier 4 JobSpy still use the date or "X hours ago" checks. Tier 4 `extra_boards` has its own snapshot (`output/board_job_snapshot.json`, written by `fetch_boards.py`, same rules).
- Report one line per run (boards ok, fresh by date, fresh by new-id only, baseline boards, anomalies) in the working notes. The final user-facing output stays the CSV path only.
